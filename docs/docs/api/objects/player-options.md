# PlayerOptions

All parameters are optional. You also only need to specify the ones you want to update.

`PlayerOptions` are consumed by the one-time `setupPlayer()` lifecycle operation; they are not a runtime backend selection surface. Use `setPlaybackBackend({ type: 'standard' })` or `setPlaybackBackend({ type: 'pingPong' })` for runtime backend changes; the `pingPong` variant optionally accepts `engineMode: 'orchestratedDualEngine'`. `setPlaybackBackend()` is the sole runtime backend mutation API, and RNTP owns the ping-pong engines and crossfade orchestration.

The setup-only `crossfadeEngineMode` option remains source-compatible but is deprecated. Both `orchestratedDualEngine` and the historical `legacyHybrid` value select the same RNTP-owned orchestrated engine; no legacy playback owner remains.

| Param | Type | Description | Android | iOS |
|-------|------|-------------|---------|-----|
| `minBuffer` | `number` | Minimum duration of media that the player will attempt to buffer in seconds. | ✅ | ✅ |
| `maxBuffer` | `number` | Maximum duration of media that the player will attempt to buffer in seconds. | ✅ | ❌ |
| `backBuffer` | `number` | Duration in seconds that should be kept in the buffer behind the current playhead time. | ✅ | ❌ |
| `playBuffer` | `number` | Duration of media in seconds that must be buffered for playback to start or resume following a user action such as a seek. | ✅ | ❌ |
| `maxCacheSize` | `number` | Maximum cache size in kilobytes. | ✅ | ❌ |
| `iosCategory` | [`IOSCategory`](../constants/ios-category.md) | An [`IOSCategory`](../constants/ios-category.md). Sets on `play()`. | ❌ | ✅  |
| `iosCategoryMode` | [`IOSCategoryMode`](../constants/ios-category-mode.md) | The audio session mode, together with the audio session category, indicates to the system how you intend to use audio in your app. You can use a mode to configure the audio system for specific use cases such as video recording, voice or video chat, or audio analysis. Sets on `play()`. | ❌ | ✅  |
| `iosCategoryOptions` | [`IOSCategoryOptions[]`](../constants/ios-category-options.md) | An array of [`IOSCategoryOptions`](../constants/ios-category-options.md). Sets on `play()`. | ❌ | ✅  |
| `waitForBuffer` | `boolean` | Indicates whether the player should automatically delay playback in order to minimize stalling. Defaults to `true`. @deprecated This option has been nominated for removal in a future version of RNTP. If you have this set to `true`, you can safely remove this from the options. If you are setting this to `false` and have a reason for that, please post a comment in the following discussion: https://github.com/doublesymmetry/react-native-track-player/pull/1695 and describe why you are doing so. | ✅ | ✅ |
| `autoUpdateMetadata` | `boolean` | Indicates whether the player should automatically update now playing metadata data in control center / notification. Defaults to `true`. | ✅ | ✅ |
| `autoHandleInterruptions` | `boolean` | Indicates whether the player should automatically handle audio interruptions. Defaults to `false`. | ✅ | ✅ |
| `crossfade` | `boolean` | Enables the RNTP-owned ping-pong playback backend during one-time setup. Defaults to `false`. | ✅ | ✅ |
| `stallTimeoutMs` | `number` | How long, in milliseconds, any of the player's waits for a track (crossfade load, seek and play start; standard backend readiness and seek) may go on with no progress (no new media downloaded or buffered) before it fails. Defaults to `10000`. On Android, the players' HTTP connect and read timeouts follow it too (instead of ExoPlayer's fixed 8 s), from the next request, on every track (a loaded or preloaded one too); the crossfade and the standard player alike. A slow load that keeps progressing is only stopped by the wait's own total limit (the options below). A value that is not a number from 1 to 2147483646 is ignored. Also accepted by `updateOptions` (applies to the next wait); left out, the current value is kept; other options left out of an `updateOptions` call (capabilities, progress interval…) are reset, so pass it together with your usual options. | ✅ | ✅ |
| `prepareTimeoutMs` | `number` | Crossfade backend: the total limit, in milliseconds, for a track to become ready, even while it progresses (`stallTimeoutMs` fails a stalled load sooner). Android: the whole load and every seek (`crossfade_prepare_timeout` / `crossfade_seek_timeout`); iOS: the whole load (playable stage, ready item, seek to the start position, preroll) and every seek. On iOS the stage before the asset is playable has no progress signal, so only this limit ends it there; `stallTimeoutMs` applies from the moment the asset is playable. An iOS crossfade seek (which had no limit before) now fails after `stallTimeoutMs` with no progress or at this limit, and the player then reports an error state. Defaults to `60000`. Same bounds and rules as `stallTimeoutMs`, also accepted by `updateOptions` (applies to the next load). | ✅ | ✅ |
| `playStartTimeoutMs` | `number` | Crossfade backend (iOS and Android; a failed start pauses and reports `crossfade_play_start_timeout` on Android, and a crossfade whose incoming song does not start reports `crossfade_start_failed` while the outgoing song plays on; the resume of a fade paused mid-way does not wait): the total limit, in milliseconds, for playback to start (after `play`, a load that plays at once, or the incoming song of a crossfade). Defaults to `60000`. A backend switch and the play used to resume after an interruption wait at most this plus `prepareTimeoutMs` plus 5 s (at least 10 s). Same bounds and rules as `stallTimeoutMs`. | ✅ | ✅ |
| `standardReadyTimeoutMs` | `number` | Standard backend: the total limit, in milliseconds, for a track restored by a backend switch to be ready. Defaults to `60000`. Same bounds and rules as `stallTimeoutMs`. | ✅ | ✅ |
| `standardSeekTimeoutMs` | `number` | Standard backend (iOS and Android): the total limit, in milliseconds, for a seek (`standard_seek_timeout`). Defaults to `60000`. The wait for the item to load before the seek is issued (or behind another seek) is bounded by this limit only; once issued, `stallTimeoutMs` applies to the buffered position, the only signal the standard player exposes. Same bounds and rules as `stallTimeoutMs`. | ✅ | ✅ |
| `incomingStallGraceMs` | `number` | Crossfade backend: how long, in milliseconds, a crossfade waits for the incoming track to start moving before it falls back to playing that track alone (`incoming_stalled`). Defaults to `2000`. Same bounds and rules as `stallTimeoutMs`; also accepted by `updateOptions` (read at every fade step). | ✅ | ✅ |
| `initialBitrateEstimateBps` | `number` | Android (crossfade and standard backends): the bandwidth, in bits per second, each track starts from before the player has measured the network. An adaptive (HLS/DASH) track starts at the highest rendition whose bitrate fits about 70 % of it (ExoPlayer's bandwidth fraction), or at the lowest when none fits, and climbs as the player measures. Defaults to `96000`. Also accepted by `updateOptions`. It is a start-of-track estimate: a new value is used at the next track start; the playing track is not reset mid-track (its rendition follows the measured bandwidth). A value that is not a number from 1 to 2147483646 is ignored. | ✅ | ❌ |
| `crossfadeEngineMode` | `'orchestratedDualEngine' \| 'legacyHybrid'` | Deprecated source-compatibility alias. Both values select the orchestrated dual engine; omit for new integrations. | ❌ | ✅ |
| `androidAudioContentType` | `boolean` | The audio content type indicates to the android system how you intend to use audio in your app. With `autoHandleInterruptions: true` and `androidAudioContentType: AndroidAudioContentType.Speech`, the audio will be paused during short interruptions, such as when a message arrives. Otherwise the playback volume is reduced while the notification is playing. Defaults to `AndroidAudioContentType.Music` | ✅ | ❌ |
